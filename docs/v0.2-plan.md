## 1. 决策快照

本 plan 的所有具体动作都源于以下决策。如果某个决策需要回退,plan 的对应阶段需要重写。

| 维度 | 决定 | 来源 |
|---|---|---|
| corpus 组织 | PARA 四层: Projects / Areas / Resources / Archives | 借鉴 Tiago Forte PARA 方法 |
| 项目内部 | 5 固定子目录(01-方案 / 02-章节 / 03-纪要 / 04-调研 / 05-附图)+ 99-其他兜底 | 视觉浏览痛点驱动 |

| path_map.yaml 定位 | 退化为"buckets 语义说明 + hint 关键词 + explicit_mappings 偏好覆盖",不再是规则匹配表 | 同上 |
| Archives 归档 | 主路径手动 mv,独立脚本扫 6 个月活跃度做候选提醒,不自动 mv | 项目可能只是暂停 ≠ 已归档 |
| 场景体系 | scope (PARA) × behavior (Broder/Jansen 4 类) 双轴解耦 | scope 由 LLM 按问法关键词路由,behavior 由 LLM 内部识别;用户都不被问 |
| 4 类检索行为 | 单点定位 / 盘点 / 决策溯源 / 模糊探索 | Jansen 5 子类合并 find+directed |
| 格式扩展 | 嵌入图 + 嵌入表 + vsdx 必做;xmind 转 PNG 走 vision;shp 不做;odf 简单兼容 | 工作素材真实占比驱动 |
| frontmatter | type / date / project / tags 四字段,ingest 自动注入,无则 fallback | LLM 二档过滤精度需求 |
| search.py 增强 | 加 `--project` 单参数,不加 `--intent` / `--domain`(行为识别在 prompt 内做) | 保持 search.py 薄包装器定位 |
| explicit_mappings | 保留字段,默认空,作为 AI 路由的兜底手段 | Hugin v1.1 拍板 |

### 2.2 ingest 范式: AI 语义路由

v0.2 ingest 流程的核心范式切换 —— **从"规则匹配路由"切换到"AI 语义路由"**。

**为什么**: 真实操作者是 AI(Claude Code 在 agent loop 里跑 ingest)。AI 看到子目录叫"规范资料",知道是 resources;看到"投标资料/",知道是 areas;看到"智慧城市可视化平台",知道是项目。这种判断写不进正则规则,但 AI 一眼就能看出。把判断硬塞进 yaml 规则是低效的反 AI 设计。

**ingest.py 的新定位**: 退化为两个机械动作

- `ingest.py --scan-only <源目录>`: 扫描目录结构,输出清单(`logs/routing_request.json`),不做任何判断
- `ingest.py --execute-plan <plan.json>`: 按 AI 给的方案执行迁移 + frontmatter 注入,不做任何判断

**完整流程从用户角度**:

```
用户对 Claude Code 说: "把 D:/某客户/智慧城市可视化平台 入库"

Claude Code (一气呵成,用户不被打扰):
  1. Bash 调 python scripts/ingest.py --scan-only D:/某客户/智慧城市可视化平台
     → ingest.py 扫目录树,生成 logs/routing_request.json
  2. Read logs/routing_request.json + path_map.yaml + CLAUDE.md 第 6 节
     → AI 内部判断路由方案 → 写 logs/routing_plan.json
     → 展示方案给用户看一眼(不强制确认,有异议用户打断)
  3. Bash 调 python scripts/ingest.py --execute-plan logs/routing_plan.json
     → 按方案执行迁移 + frontmatter 注入
  4. 报告结果
```

判断逻辑全在 AI 这边,ingest.py 代码更简单。

### 2.3 scope × behavior 双轴检索架构

**scope 维度(在哪找)**: 由 LLM 在 CLAUDE.md 第 5 节按用户问法关键词自动路由到 PARA 一级目录。

**behavior 维度(怎么整合)**: 由 LLM 在 CLAUDE.md 步骤 0(新增)按用户问法关键词识别 4 类行为,选对应整合方式。

| 行为 | 触发词特征 | 整合方式 |
|---|---|---|
| **单点定位** | "那个 / 某 / 上次 / 什么时候 / 谁" | 找最精确出处,完整引用 + 行号 |
| **盘点** | "哪些 / 几个 / 全部 / 列一下" | 多源遍历,列表化输出 + 计数 |
| **决策溯源** | "为什么 / 优劣 / 对比 / 选 X 不选 Y" | 多源按时间线/角度组织,带对比 |
| **模糊探索** | 问法宽泛,只有主题词没有指向 | 给 3-5 个候选文件 + 简短摘要,让用户挑 |

两轴正交: 在 Projects 里可以做 4 类行为中任意一种,在 Areas 里也可以。**用户不被问任何选择题**。

## 3. Review 协议

每阶段做完前,**必须**走 Review 流程:

1. **自查**: Hugin 对照阶段末尾的 "Review 检查清单",逐条标 YES / NO / 部分
2. **证据收集**: 对每条 YES,在 `tests/查询记录.md` 或本 plan 的对应阶段尾部记 1 行证据
3. **裁决会话**: Hugin 把 Review 清单结果发给 Claude(web 或 Code),由 Claude 给出三种判断之一:
   - **PASS**: 可以进下一阶段
   - **CONDITIONAL_PASS**: 可以继续,但有 X/Y/Z 留作 W 系观察点(沿用 tender-writer V3 的 W 系机制)
   - **FAIL**: 当前阶段必须返工,Claude 指出哪条不达标
4. **记录**: 裁决结果写入 `tests/v0.2-plan-progress.md`(新建文件,沿用现有 tests/ 治理风格)

不允许跳过 Review 进下一阶段。如果某条 Review 条目执行时发现不合理,先回到本 plan 修订对应阶段(Plan 修订也是 PER 协议的一部分),不要硬过。

#### 步骤 1.3: 写迁移脚本 `scripts/migrate_v01_to_v02.py`

迁移老 corpus(v0.1)到新结构(v0.2)。**这是 plan 范围内唯一的"批量改 corpus"操作**,不涉及用户源目录。

```python
# scripts/migrate_v01_to_v02.py 设计 sketch (不是最终代码)

"""
v0.1 → v0.2 corpus 迁移脚本

设计原则:
1. 两阶段执行: dry-run (默认) → commit (--commit flag)
2. 可重入: 跑过一次部分失败,再跑能从断点继续
3. 不破坏原数据: dry-run 阶段绝对不动文件; commit 阶段先复制再删原
4. 全程日志: 记到 logs/migration_v02_<timestamp>.jsonl
"""

import argparse, shutil, json
from pathlib import Path

# v0.1 老 bucket → v0.2 新 bucket 的固定对应(仅针对老 corpus 重组)
V01_TO_V02_BUCKET_MAP = {
    "01-历史方案": "01-projects",
    "02-投标章节": "02-areas/投标章节模板",
    "03-技术决策": "02-areas/技术方法论",
    "04-个人记忆": "03-resources/培训与调研",
}

def discover_files(corpus_root: Path) -> list[dict]:
    """扫描 v0.1 corpus 所有文件,生成迁移计划"""
    plans = []
    for old_bucket, new_bucket in V01_TO_V02_BUCKET_MAP.items():
        old_dir = corpus_root / old_bucket
        if not old_dir.exists():
            continue
        for f in old_dir.rglob("*"):
            if f.is_file() and not is_temp_or_hidden(f):
                relative = f.relative_to(old_dir)
                new_path = corpus_root / new_bucket / relative
                plans.append({
                    "src": str(f),
                    "dst": str(new_path),
                    "action": "move",
                    "reason": f"v01_to_v02_bucket_map[{old_bucket}]",
                })
    return plans

def execute_commit(plans: list[dict]):
    """实际执行迁移,可重入(已迁移过的跳过)"""
    for plan in plans:
        src, dst = Path(plan["src"]), Path(plan["dst"])
        if dst.exists():
            log_skip(plan, reason="dst_already_exists")
            continue
        dst.parent.mkdir(parents=True, exist_ok=True)
        shutil.copy2(src, dst)
        if dst.exists() and dst.stat().st_size == src.stat().st_size:
            src.unlink()
            log_success(plan)
        else:
            log_failure(plan, reason="copy_verify_failed")

def main():
    parser = argparse.ArgumentParser()
    parser.add_argument("--commit", action="store_true", help="实际执行(默认 dry-run)")
    parser.add_argument("--corpus", default="corpus")
    args = parser.parse_args()
    
    plans = discover_files(Path(args.corpus))
    
    if not args.commit:
        write_dry_run_report(plans, Path("logs"))
        print(f"Dry-run done. {len(plans)} files planned. Run with --commit to execute.")
    else:
        confirm = input(f"About to migrate {len(plans)} files. Proceed? [y/N]: ")
        if confirm.lower() != 'y':
            print("Aborted.")
            return
        execute_commit(plans)

if __name__ == "__main__":
    main()
```

**关键设计**:
- dry-run 默认,commit 需要 `--commit` 显式打开 + 交互确认
- 复制成功后才删原文件(不是 `shutil.move`),避免迁移中断时数据丢失
- 可重入(dst 存在则跳过)

```python
def inject_frontmatter(md_file: Path, frontmatter: dict):
    """
    - 已有 frontmatter: 保留,只补缺失字段
    - 无 frontmatter: 完整注入
    - 格式坏的 frontmatter: 跳过(保守)
    """
    content = md_file.read_text(encoding="utf-8")
    
    if content.startswith("---\n"):
        end_marker = content.find("\n---\n", 4)
        if end_marker > 0:
            existing_fm_text = content[4:end_marker]
            existing_fm = yaml.safe_load(existing_fm_text)
            for k, v in frontmatter.items():
                if k not in existing_fm:
                    existing_fm[k] = v
            new_fm_text = yaml.safe_dump(existing_fm, allow_unicode=True, default_flow_style=False)
            content = f"---\n{new_fm_text}---\n{content[end_marker+5:]}"
    else:
        fm_text = yaml.safe_dump(frontmatter, allow_unicode=True, default_flow_style=False)
        content = f"---\n{fm_text}---\n\n{content}"
    
    md_file.write_text(content, encoding="utf-8")
```

```python
"""扫描 01-projects/*/,6 个月以上无新文件的项目作为归档候选"""

ARCHIVE_THRESHOLD_DAYS = 180

def scan_archive_candidates(corpus_root: Path) -> list[dict]:
    projects_dir = corpus_root / "01-projects"
    candidates = []
    threshold = datetime.now() - timedelta(days=ARCHIVE_THRESHOLD_DAYS)
    
    for proj_dir in projects_dir.iterdir():
        if not proj_dir.is_dir():
            continue
        latest_mtime = max(
            (f.stat().st_mtime for f in proj_dir.rglob("*") if f.is_file()),
            default=0,
        )
        latest_dt = datetime.fromtimestamp(latest_mtime)
        if latest_dt < threshold:
            candidates.append({
                "project": proj_dir.name,
                "latest_activity": latest_dt.strftime("%Y-%m-%d"),
                "days_inactive": (datetime.now() - latest_dt).days,
                "file_count": sum(1 for _ in proj_dir.rglob("*") if _.is_file()),
            })
    return candidates
```

```
## 2.0 步骤 0: 检索行为识别(v0.2 新增)

每次查询的第一件事是识别检索行为模式。这决定 LLM 在后续步骤如何整合答案。

4 类行为定义:

| 行为 | 触发词关键词(优先级从高到低) | 整合方式 |
|---|---|---|
| 单点定位 | "那个/某/上次/什么时候/谁/哪个文件" | 找最精确出处,完整引用 + 行号,单文件即可 |
| 盘点 | "哪些/几个/全部/列一下/都有什么" | 多源遍历,列表化输出 + 计数,跨项目时按项目分组 |
| 决策溯源 | "为什么/优劣/对比/选 X 不选 Y/怎么决定的" | 多源按时间线/角度组织,带对比,引用要齐 |
| 模糊探索 | 问法宽泛,只有主题词没有指向词 | 给 3-5 个候选文件 + 简短摘要,让用户挑;不要直接整合答案 |

触发词优先级冲突:
- "为什么" + "某/那个" → 单点定位(指向词优先)
- "为什么" 单独出现 → 决策溯源
- "哪些" + "为什么" → 盘点
- 无明显主导触发 → 模糊探索(让用户挑比硬猜安全)

行为识别写入轮次状态段:

【轮次状态段 N=1】
- 轮次号: 1
- 检索行为: 单点定位 / 盘点 / 决策溯源 / 模糊探索
- 行为判定依据: "用户问题中含 XXX 关键词"
- 本轮检索词: [...]
- ...(其他字段同 v0.1)

行为稳定性:
- 轮 1 状态段写定行为,后续轮次保持不切换
- 如轮 N 发现判错(如判"单点定位"但命中数远超预期 → 用户在做盘点),
  轮 N+1 状态段第一行明示 "行为校正: 单点定位 → 盘点,理由 XXX",再继续

行为决定的不是 scope,而是整合方式。scope 由步骤 1 的场景路由决定。两个维度独立。
```

```markdown
7. Bash 调 `python scripts/ingest.py execute-plan logs/routing_plan.json`

### 6.2 判断流程

#### Step A: 检查 explicit_mappings 优先

对每个源目录/文件,先扫 path_map.yaml 的 `explicit_mappings` 字段。
匹配到 source 的,直接用对应 target,**跳过后续判断**。

#### Step B: 顶层目录性质判断

若 explicit_mappings 未命中,判断源目录顶层是什么类型:

- **项目目录**: 看目录内容,如果包含总体方案/架构设计/纪要/调研等"具体工作单元交付物"迹象 → 整体落到 `01-projects/<原顶层目录名>/`,但内部要进一步分流(Step C)
- **areas 类**: 顶层名含"产品" / "方法论" / "投标章节" / "handbook" 关键词 → 整体落到 `02-areas/<合适子目录>/`
- **resources 类**: 顶层名含"标准" / "规范" / "国标" / "行业研究" / "培训" 关键词 → 整体落到 `03-resources/<合适子目录>/`
- **archives 类**: 顶层名含"已交付" / "已归档" / "已完成" → 落到 `04-archives/<原顶层目录名>/`
- **难判断**: 用 Read 抽样看 1-2 个核心文件,基于内容判断,不只看目录名

#### Step C: 项目内部子目录脱钩判断

若 Step B 落到 projects,对项目内的每个子目录做脱钩判断:

判断要点: 这个子目录是**项目特有**还是**跨项目可复用**?

- `标准/` `规范/` `国标/` 等 → 跨项目通用资源 → 脱钩到 `03-resources/国标行标/`,文件名加项目前缀消歧(如 `<项目名>_<原文件名>`)
- `行业研究/` `调研报告/` `竞品/` → 脱钩到 `03-resources/` 对应子目录
- `培训/` `分享/` → 脱钩到 `03-resources/培训与调研/`
- `纪要/` `调研/` `方案/` → 项目特有,留在项目内,按 Step D 映射到 5 子目录
- `素材/` `图片/` `截图/` → 留在项目内,落到 `05-附图/`
- `合同/` `验收/` `招标/` → 项目特有(合同是项目交付一部分),留在项目内 `99-其他/`
- **模糊的子目录 → 不要硬猜,留在项目内 `99-其他/`**

#### Step D: 单文件级路由(项目内 5 子目录映射)

对每个落到项目内的文件,判断属于哪个子目录:

- 文件名前缀 `方案-` / `设计-` / `架构-` → `01-方案/`
- 文件名前缀 `章节-` → `02-章节/`
- 文件名前缀 `纪要-` / `会议-` → `03-纪要/`
- 文件名前缀 `调研-` / `访谈-` → `04-调研/`
- 图片扩展名(.png/.jpg/.jpeg/.gif/.bmp/.webp) → `05-附图/`
- 无前缀但内容明确 → 用 Read 看前 20 行,按内容判断
- 实在判断不出 → `99-其他/`

### 6.3 输出 schema

写到 `logs/routing_plan.json`,schema 见 docs/v0.2-plan.md 阶段 2 步骤 2.3。

每条 item 必须包含:
- `src_abs`: 源文件绝对路径
- `target_bucket`: 一级目录(01-projects / 02-areas / 03-resources / 04-archives)
- `target_project`: 仅当 bucket=01-projects 时有值
- `target_subdir`: 项目内 5 子目录 / areas-resources 的二级子目录
- `target_filename`: 目标文件名(脱钩到 resources 时加项目前缀)
- `frontmatter`: 注入到 .md 的 dict (type/date/project/tags)
- `ai_reason`: 路由判断理由(1-2 句话,用于用户快速审)

### 6.4 约束

- **不要主动改源目录命名** —— 路由完全基于读取
- **不要把可能是 resources 的内容(标准/国标)留在项目内** —— 跨项目可复用资源必须脱钩
- **不要把项目特有内容(纪要/调研)脱钩到 areas** —— 这些内容跟项目绑定
- **难判断的优先 99-其他/**,不要瞎归到 areas/resources —— 宁可保守归类
- **整个子目录决定前,Read 抽样看 1-2 个核心文件**,基于内容判断,不只看文件名
- **重名文件冲突时自动加项目前缀消歧**,不要覆盖原文件
- **archives_hint 关键词命中时倾向归到 archives**,但用 mtime 二次确认

### 6.5 用户介入点

routing_plan.json 产出后,展示给用户。用户可能:
- 没异议 → 直接跑 execute-plan
- 有异议 → 用户告诉你哪条不对,你修订 plan 后再展示

不需要每次都让用户敲 y 确认 —— 展示即可,用户沉默视为认可。
```
