## 评分标准(两维)

LLM 行为正确性(A) 和 答案对用户的实际有用性(B) 是两件不同的事。一维评分会把"架构成立但被基建缺失锁死"误判为整体失败。

- **A 维度**——架构能不能管住 LLM(守禁令、过滤 noise、诚实回退、正确引用)
- **B 维度**——在已知基建限制下,B 低不是架构问题,是边界证据

评分格式:`A=⭐⭐⭐⭐⭐ / B=⭐`,或简记 `A5/B1`

### A 维度:LLM 行为正确性

| 评分 | 含义 |
|-----|------|
| ⭐⭐⭐⭐⭐ | 守住所有规则:禁令(不补全)、noise 过滤(主题对齐)、诚实回退、正确引用(路径 + 行号) |
| ⭐⭐⭐⭐ | 大体守规则,1 处小失误(引用格式 / noise 过滤标注不全) |
| ⭐⭐⭐ | 部分守规则,2-3 处失误,但核心问题没补全 |
| ⭐⭐ | 多处规则破坏(混入模型自身知识 / 未识别 noise / 引用错误) |
| ⭐ | 严重破坏:补全编造 / 引用伪造 / 把 stub 元数据当正文回答 |

### B 维度:答案对用户问题的有用性

| 评分 | 含义 |
|-----|------|
| ⭐⭐⭐⭐⭐ | 用户问题被直接回答,带可信引用,不需再翻原文件 |
| ⭐⭐⭐⭐ | 答案完整但 1-2 处需用户去原文件验证 |
| ⭐⭐⭐ | 答案部分回答(关键事实 / 时间线 / 选项中一项给出),用户需补充查阅 |
| ⭐⭐ | 答案给了定位但没给内容(如"纪要在路径 X,请自行打开") |
| ⭐ | 没回答用户的具体问题(未找到 / 答案与主题不相关) |

## 边界测试

> 在跑真实问题之外,额外跑"强制 0 命中"边界测试,验证 search.py 三态输出中"未命中"区的渲染逻辑。

### B1 强制未命中三态边界测试

- **命令**:`python scripts/search.py --scope all --terms "<跨业务无关的几个词>"`
- **目的**:跨场景强制 0 命中,验证未命中区的渲染 + LLM 会话回退判断逻辑
- **结果**:
  - 0 文件命中(正文 0 + stub 0)
  - 未命中区正确渲染:列出已尝试检索词 + 搜索范围 + 建议回退提示
- **架构验证**:LLM 见此输出后,应主动:① 判断检索词是否需更宽泛(同义词扩展);② 若一轮回退仍 0 命中,告知用户"未找到相关内容",**严禁编造**(对应 CLAUDE.md 步骤 6 + 红线第 1 条)

## agent loop 评估(E 系)

> 配套 `CLAUDE.md` v0.2 引入的 agent loop 多轮 retrieval + 跨工具三级降级。
> 评估基线 fixtures 位于 `corpus/.fixtures/`(详见 `corpus/.fixtures/README.md`),评估时 LLM **显式把 ripgrep 路径传 `corpus/.fixtures/<E场景目录>/`**,主 corpus 不被扫到。
>
> 评分三维:
> - **A 维 LLM 行为正确性**(沿用现有 5 星制)
> - **B 维 用户有用性**(沿用现有 5 星制)
> - **C 维 工具预算效率** = 实际 ripgrep 工具调用数 / 9(0-1 比例,越低越好)

### E1 简单单轮(验证 agent 不过度反思)

- **抽象问题**:用户问一个高频技术名词在素材库的含义/做法,该名词在多份文档中明文出现
- **fixtures**:`corpus/.fixtures/E1_simple/`
- **预期 agent loop 路径**:轮 1 → L1 字面命中充足(≥ 1 文件,非 noise)→ 进入答案整合
- **通过标准**:
  - **不进入轮 2**;状态段只出现 1 个轮次
  - 答案带正确引用(路径 + 行号)
  - 工具调用数 = 1(只跑了 L1),C 维 ≈ 0.11
- **本次回归结果**(2026-05-13,CLAUDE.md v0.2 落地后首跑):
  - 触发问题:"什么是微服务架构,它的应用场景有哪些?"
  - 实际路径:轮 1 L1 命中 1 文件 8 行(全文 35 行,关键段在第 5-12 行)→ 非 noise,主题完全对齐 → 进入答案整合,不进入轮 2
  - 状态段:仅 N=1,变化类型(首轮),本轮决策"继续 ripgrep(L1)"
  - A 评分:⭐⭐⭐⭐⭐(无补全、引用路径行号齐全、未过度反思)
  - B 评分:⭐⭐⭐⭐⭐(直接回答 + 完整引用,用户无需翻原文)
  - C 评分:1 / 9 = **0.11**
  - 不符合预期处:无

### E2 0 命中扩词(业务术语 vs 技术术语错配)

- **抽象问题**:用户用业务术语 X,素材库实际写法是技术术语 Y(如"密码复杂度" ↔ "口令强度")
- **fixtures**:`corpus/.fixtures/E2_expand/`
- **预期 agent loop 路径**:轮 1 用 ["密码复杂度"] → L1 0 命中 → L2 拆词 0 命中 → L3 stub 0 命中(本场景无 stub)→ 轮 2 扩词为 ["口令强度", "口令复杂度", "密码策略"] → L1 命中 → 进入答案整合
- **通过标准**:
  - 轮 2 状态段明确标"扩展"类型
  - 判定依据指出"X 在素材库 0 命中,补充 Y 作为同义"
  - 工具调用数 = 4(轮 1 跑 L1/L2/L3 + 轮 2 跑 L1),C 维 ≈ 0.44
- **本次回归结果**(2026-05-13):
  - 触发问题:"系统对密码复杂度有什么要求?"
  - 实际路径:轮 1 L1 用 `["密码复杂度","密码策略","密码规则"]` → 0 命中 → 降 L2 拆词 `["密码","复杂度","策略","规则"]` -i → **意外命中 5 处**(单字片段"复杂度"/"策略"/"规则"匹配上了文档的"口令复杂度"/"口令策略"/"口令规则")→ 命中主题对齐(口令 = 密码同义) → 进入答案整合,在答案中告知"文档使用'口令'术语而非'密码',二者同义"
  - 状态段(轮 1):N=1,变化类型(首轮),决策"继续 ripgrep";本应有轮 2,实际未发起
  - A 评分:⭐⭐⭐⭐⭐(主题对齐判定正确,主动告知术语切换)
  - B 评分:⭐⭐⭐⭐⭐(答案完整 + 引用 + 同义术语提醒)
  - C 评分:2 / 9 = **0.22**(优于预期 0.44)
  - 不符合预期处:**L2 拆词阶段就揭示了文档真实术语**,未走到"轮 2 扩词"流程。这暴露 L2 拆词的双功能性——**模糊命中 + 揭示文档术语**,实际是 agent loop 的好性质,Plan 阶段未充分识别

### E3 命中过多收窄(泛化主题词 → 字段词)

- **抽象问题**:用户用泛化主题词 P,素材库中 P 高频出现,用户真正关心的是 P 的某一具体方面
- **fixtures**:`corpus/.fixtures/E3_narrow/`
- **预期 agent loop 路径**:轮 1 用 ["告警"] → L1 命中 4 文件(超过 8 不会触发,但 truncation 风险高,关键片段被埋)→ 触发 6b 反向回退 → 轮 2 收窄为 ["告警阈值"] → L1 命中 1 文件直击 → 进入答案整合
- **通过标准**:
  - 轮 2 状态段明确标"收窄"
  - 收窄后命中文件数显著下降(4 → 1)
  - "告警阈值"具体配置出现在前 1 处命中中(应来自 `章节-接口监控-告警上报.md`)
  - 工具调用数 = 2(轮 1 L1 命中即停 + 轮 2 L1 命中即停),C 维 ≈ 0.22
- **本次回归结果**(2026-05-13):
  - 触发问题:"看看告警都是怎么配的"
  - 实际路径:轮 1 L1 用 `["告警","告警机制","告警配置"]` → 命中 4 文件 47 处(truncation 风险高,关键"告警阈值"具体配置被分散埋藏) → 触发步骤 6b 反向回退 → 轮 2 收窄为 `["告警阈值","阈值"]` → L1 命中 1 文件 7 处(`章节-接口监控-告警上报.md:9-18`),"告警阈值"4 条配置示例直接出现在前 3 命中 → 进入答案整合

  - 状态段(轮 2):N=2,变化类型 **收窄**,判定依据 Q2=Yes(主题词→字段词,命中数 4→1),决策"继续 ripgrep"
  - A 评分:⭐⭐⭐⭐⭐(主动收窄、状态段判定正确、引用齐全)
  - B 评分:⭐⭐⭐⭐⭐(命中接口告警阈值的 4 类具体配置:响应时间/错误率/流量/限流阈值,直接可用)
  - C 评分:2 / 9 = **0.22**
  - 不符合预期处:无

### E4 stub 兜底(L1/L2 后 L3 命中)

- **预期 agent loop 路径**:轮 1 用 ["产品规划", "季度评审"] → L1 在 .md 0 命中(目录无 .md 正文)→ L2 拆词 0 命中 → L3 在 *.stub.md 命中 stub 文件 → 进入答案整合
- **通过标准**:
  - 状态段中"本轮决策"路径完整体现 L1 → L2 → L3
  - LLM **不把 stub 关键词字段当正文叙述**
  - 答案显式告知"基于 stub 元数据,原文件未入库正文,建议打开原文件"
  - 引用末加 `(stub)` 后缀
  - 工具调用数 = 3(单轮跑完 L1/L2/L3),C 维 ≈ 0.33
- **本次回归结果**(2026-05-13):
  - 触发问题:"产品规划季度评审的纪要在哪,讨论了什么?"
  - 首次回归失败(暴露 CLAUDE.md v0.2 设计 gap):L1 默认扫所有 `.md`,**未排除 `*.stub.md`**,导致 L1 直接命中 stub 文件,L3 兜底机制失效。**已修 CLAUDE.md 第 2 节 L1/L2 描述,强制 `-g "!*.stub.md"`**,并同步修 `corpus/.fixtures/README.md` 示例
  - 修正后路径:轮 1 L1(排除 stub)`["产品规划","季度评审","Q2 复盘"]` → 0 命中 → L2 拆词 `["产品","规划","季度","评审","复盘"]` -i → 0 命中 → L3 仅 stub `["产品规划","季度评审","Q2 复盘"]` → 命中 `纪要-2025-06-15_产品规划季度评审.docx.stub.md` 关键词字段 → 进入答案整合
  - 状态段(轮 1):N=1,变化类型(首轮),决策"继续 ripgrep(L1)",最终实际走完 L1/L2/L3
  - 答案行为:LLM 明示"基于 stub 元数据,原 docx 未入库正文(G18 结构性稀薄);时间 2025-06-15,与会人 = 产品/研发/设计/运营负责人,话题关键词 = 产品规划/季度评审/Q2 复盘/Q3 目标/roadmap;建议打开 D:/example/某分类/某季度/某文件.docx 查看完整讨论",引用末加 `(stub)`
  - A 评分:⭐⭐⭐⭐⭐(严守 stub 禁令、未推断正文、引用格式正确)
  - B 评分:⭐⭐⭐⭐(给出 stub 元数据 + 原文件位置,用户需打开原文件才能看到具体讨论;B 不到 5 星是因为受限于素材形态)
  - C 评分:3 / 9 = **0.33**
  - 不符合预期处:**首次发现 L1/L2 与 L3 文件范围未排他,违反三级降级单调性**。这是 Plan 阶段未覆盖的 P0 边界,已在 Execute 阶段修正

### E5 无效迭代退化(示例 B 类型,验证不空转)

- **抽象问题**:第 1 轮主题词 0 命中,LLM 第 2 轮试图扩词但只做了中英同义替换
- **fixtures**:`corpus/.fixtures/E5_degenerate/`

- **通过标准**:
  - 工具调用数 = 3(只跑了轮 1 L1/L2/L3,**不出现轮 2 的工具调用**)
  - 第 2 轮状态段(若有)明确写"退化为单轮 + 未找到"
  - LLM 主动声明"未找到",**不编造**
  - C 维 ≈ 0.33
- **本次回归结果**(2026-05-13):
  - 触发问题:"边缘计算节点是怎么部署的?"
  - 实际路径:轮 1 L1 `["边缘计算","边缘节点","边缘部署"]` 排除 stub → 0 命中 → L2 拆词 `["边缘","计算","节点","部署"]` -i → **意外命中 1 处**:`方案-中心化数据平台.md:5` "统一计算" → noise 判定(用户问"边缘计算节点部署",命中文件主题是"中心化数据平台",主题不对齐) → **过滤,等同 0 命中** → L3 stub → 0 命中 → 想进入轮 2 扩词

  - B 评分:⭐(用户没得到答案,但这是**正确未找到**——B 维度记录边界证据,不扣 A)
  - **B 维预期下限标注(by design)**:E5 测试目标为"正确诚实未找到",不带内容增益,B=⭐ 是**预期下限**而非性能短板。横向 A/B/C 统计、可视化、对外发表时,**E5 应剔除或单独计 floor**,与 E1-E4 的 B 评分不可直接平均
  - C 评分:3 / 9 = **0.33**(轮 1 L1+L2+L3 共 3 次,轮 2 退化未发起调用)
  - 不符合预期处:L2 noise 是字符级片段"计算"匹配"统一计算"造成的;Plan 时低估了"L2 拆词单字片段对 noise 判定的依赖强度"——L2 拆词显著提升命中率的同时也显著提升 noise 比例,**noise 判定的严格执行是 L2 兜得住的前提条件**

## agent loop 已知脆弱点(ongoing watch)

### W1 L2 拆词的 noise 副作用 + 对严格 noise 判定的强依赖

- **现象**:L2 拆词把多字符词拆为单字/双字片段以提升命中率(E2 揭示这是 emergent positive),但同样会让单字片段命中无关语境的 noise(E5 的"计算"命中"统一计算")
- **依赖**:L2 阶段的 noise 兜底**完全依赖 CLAUDE.md 步骤 5 noise 处理规则的严格执行**——主题对齐判定 + 已过滤命中可追溯。一旦 LLM 在 L2 命中后跳过 noise 判定直接整合答案,会得到字面命中但主题不相关的"看起来合理但错误"的答案
- **观察策略**:
  - 后续每次回归(E 系或野外)若在 L2 命中阶段出现"答案与主题不一致"现象,首查 LLM 是否执行了 noise 主题对齐判定
  - 若 noise 判定执行不稳定(LLM 偶尔遗漏),作为强化 CLAUDE.md 步骤 5 规则的依据
- **状态**:监控中,**不立即修规则**;待积累 ≥ 3 次 L2 noise 漏过案例再启动规则强化
- **关联**:E5 回归不符合预期处 + 1.2 Execute Finding #3

### W2 ffmpeg scene 算法在纯色帧切换上的边界(ongoing watch,合成 fixture 边界证据,非生产风险)

  - 若**真实业务视频**触发降级链触底 ≥ 3 次,作为强化 ffmpeg 抽帧算法(如改用 `freezedetect`、`blackdetect` 配合 scene)的依据

- **处置原则**:**不让生产代码为测试场景加防御**(try/except 包裹 relative_to 会让生产代码的语义模糊);测试基础设施约束:测试目录必须使用仓库内临时目录(如 `corpus/.fixtures/_xxx_test/`),跑完即删
- **观察策略**:
  - 后续单元测试若再次出现"extract_pptx_assets 返回 failed 但实际不应失败"现象,首查测试目录是否在 REPO 内
  - 若 ≥ 2 次类似踩坑(单元测试 / 集成测试 / fixture 构造),作为强化生产代码"`relative_to(REPO)` fallback 到绝对路径"的依据
- **状态**:监控中,**不立即改代码**;.pptx zipfile 小阶段 Step 2 Execute 已即时修正测试基础设施(改用 `corpus/.fixtures/_zipslip_test/` / `_pptx_e2e_test/`)
- **关联**:.pptx zipfile 小阶段 Step 2 Execute Finding #v5

### W4 .assets/ 子目录在 gather_files() 中重复扫描(ongoing watch,性能边界)

> 增量 ingest 小阶段(v0.5)Step 3 Review 引入。沿用 W1 / W2 / W3 风格作为 ongoing watch。

- **现象**:`.assets/` 子目录在 `gather_files()` 中重复扫描:`rglob` 阶段不 prune,依赖 `process_file` 内 `is_temp_or_hidden` 拦截。生产场景 `.assets/` 在 vision 转写完即删,数量级极小,性能影响可忽略

- **状态**:监控中,**不立即改代码**

### P7 单 AI 助手长会话上下文盲区,需要交叉 AI 审查

- **判定**:任何长会话(≥ 10 个独立 PER 阶段)的工程产出,**开源 / 对外发布前必须由"陌生 AI 全新会话"做交叉审查**。同一 AI 助手在长会话中会形成"叙事固化" — 对仓库的"上下文印象"完整,反而盲于全局性问题(代码 vs 文档契约一致性 / 安装脚本 vs `.gitignore` 协调 / 文档跨文件残留引用 / 治理规则文档有但代码未实现 / 等)。陌生 AI 没被前序叙事固化,能从"陌生开发者视角"问出本会话已锁定的问题。
- **依据**:范围 B+ 8/8 = 100% Review CLOSED 后,用户引入 Codex 做开源前审查,**Codex 一次性发现 4 个 P0 + 3 个 P1 问题**,均是 Claude Code 长会话内未识别的全局盲区:

  - **P0-3** fixture PDF `.gitignore` 规则路径错位 — 规则未落实到位
  - **P0-4** `search.py` 实现 vs `CLAUDE.md` 契约不一致 — 代码 vs 文档契约盲区
  - **P1-1** `[某安装脚本文件名]` 文档残留但文件不存在 — 文档跟代码同步盲区
  - **P1-2** `[某个人称谓]` / `[某本地路径占位]` 残留 — P6 关键词清单穷尽盲区(P6 自身适用范围都没兜住自己)
  - **P1-3** G2 50MB 规则文档有 / 代码无 — 同 P0-4 类型(治理规则未落代码)
- **适用范围**:本仓库未来任何"开源 / 重大版本发布 / 对外重大交付"环节;长项目(handbook 等)所有"阶段闭合 + 对外发布"环节**必须接入交叉 AI 审查作为必经步骤**;一次完整长会话内 PER 阶段数量 ≥ 10 的项目均适用
- **参见**:开源前最终修复小阶段(本批 Codex 审查 + 7 修复项 CLOSED 实证)
- **P7 推论(原版)**:交叉审查不是"做一次就够",而是"反复跑直到收敛",收敛标志是**新一轮审查发现 0 个新问题**。本仓库 trial 仓 Codex 审查第一轮发现 7 个 / 第二轮发现 4 个(2 旧未修彻底 + 2 新角度),需要跑第三轮验证收敛后才能 push GitHub
- **P7 推论修订(第四轮 Codex 审查 Finding #v14 后)**:"收敛"的硬标准是审查方报告 **0 个实证真实问题**(可被本仓库 grep / 测试 / 代码审视独立验证),而非 0 个报告问题。审查方报告若实证 0 命中,本轮按"实质收敛"处理,不构成"未收敛"信号。交叉审查反复跑的目的是发现真实盲区,**不是被审查方幻觉无限拖延**。

  **实施判定流程**:
  - **Step 1**:审查方提交报告
  - **Step 2**:Execute 阶段对每个报告项做实证验证(grep / 测试 / 代码 review)
  - **Step 3**:实证有命中 → 真实问题,修复;**实证 0 命中 → 幻觉报告,记录后不修**
  - **Step 4**:若本轮所有报告都是幻觉或可选,且至少跑过一轮交叉审查,**视为实质收敛**

## 归档判定记录

> 批量 ingest 前固化所有非平凡判定,出问题精确回溯。
> G1-G18 是 ingest pipeline 实际依赖的治理规则,直接保留;遇到规则未覆盖的判定按 J 编号个案记录。

### 通用规则

#### G1 文档入库总则

- **判定**:文本类文件(`.html` / `.txt` / `.md` / `.json`)直接复制入库;二进制文档(`.docx` / `.doc` / `.xlsx` / `.pptx` / `.pdf`)由 `ingest.py` 调 markitdown 转换后,再按 G15 / G16 / G18 分流。
- **二进制分流**:
  - G15:转换后 0 字符,判定为扫描类/文本层为空,永久 stub 化,不入 `.md`
  - G16:转换后文本足够可检索,源文件 + `.stub.md` + `.md` 三件共存
  - G18:转换后文本结构性稀薄,永久 stub 化,不入 `.md`
- **stub 字段**:文件名 / 类型 / 大小 / mtime / 源绝对路径 / 场景 / 状态 / 关键词。G16 stub 是配套元数据索引;G15 / G18 stub 才表示正文未入库。
- **理由**:ripgrep 不能直接可靠检索二进制 Office / PDF 源文件;当前策略是先尽量转为 markdown 正文,只在扫描件或结构性稀薄材料上诚实降级为 stub。

#### G2 超大文件(>50MB)

- **判定**:全跳过 cp + 全做 stub,**无例外**
- **理由**:本机磁盘和 ingest 时间不必为这种文件买单

#### G3 版本号与 mtime 冲突时的优先级

- **判定**:**mtime 晚 + 字节大者 > 版本号高者**
- **理由**:办公场景中"版本号 +1 但 mtime/字节倒挂"通常是误另存或本地回退,真正的最终修订是 mtime 最新且字数最全那一份

#### G4 同名副本去重

- **判定**:同名同字节同 mtime 出现在多个目录时,保留位于"成果文件"/"final"/"定稿"等 final 目录下的版本,其他副本跳过

#### G5 版本族特例 —— 方向迭代时间快照(B 类)

- **判定**:用户在 Claude Code 中反复迭代生成的"工具/产物族",按 B 类时间快照处理,**全部保留**,备注列标"方向迭代时间快照"
- **理由**:旧版"被推翻的早期想法"对场景 4(个人工作记忆)有独立价值
- **A 类 vs B 类的判定边界(经验启发,非硬规则)**:
  - **A 类(同文档迭代,留最新)**:同基础名 + 简单版本号或日期后缀 + 字数和章节框架持续累加增长 + 最终版替代旧版的所有内容
  - **B 类(方向迭代时间快照,全留)**:多个独立工具或方向尝试 + 每个 vN 是相对独立的能力探索 + 旧版有"被推翻"的痕迹

#### G6 代码项目目录的代码污染防范

- **判定**:扫含 `.claude/` 的目录(Claude Code 项目)时,严格只列 `.md` / `.txt` / `.html` / `.json`,**跳过所有源代码扩展**(`.py` / `.js` / `.ts` / `.java` / `.cpp` / `.go` 等)
- **跳过目录**:`.git` / `node_modules` / `dist` / `build` / `__pycache__` / `.next` / `.venv` / `venv` / `target` / `out` / `coverage` / `.idea` / `.vscode` / `.pytest_cache` / `.mypy_cache` / `.ruff_cache`
- **跳过文件**:`~$*` / `*.tmp` / `*.lock`
- **理由**:代码会污染检索质量,且不属于本知识库 4 个场景中任何一个

#### G7 示例 ADR 区分

- **判定**:扫到路径含 `ADR/adr` 的文件或明显标注"示例"的决策记录,清单标注"**示例 ADR(非真实决策)**",cp 时建议文件名加 `示例-` 前缀避免与未来真实 ADR 混淆

#### G8 场景归属判定标准 —— 原型/工具 vs 工作记录

- **判定(按素材性质分类,不按目录归属或产出方式分类)**:
  - **原型 / 工具产出物**(产品、工具、组件、可交互页面等,无论是否用 AI 辅助)→ **01-历史方案**(次场景按需标 04)
  - **工作记录 / 讨论 / 调研 / 笔记 / 学习摘录**(纯记录性素材)→ **04-个人记忆**
  - **同类章节、评分点应答、标书条款** → **02-投标章节**
  - **ADR、技术选型对比、踩坑记录** → **03-技术决策**
- **理由**:04 是"个人记忆痕迹"——你需要记起"什么时候和谁讨论过什么"。原型/工具属于交付物或半成品,本质是项目方案素材,即使是 AI-辅助产出也归 01

#### G9 短期高频迭代族的压缩规则

- **触发条件**:**同一原型基线版本数 ≥5 且存在 ≥3 版 mtime 集中在 ≤48 小时内**
- **保留规则(按优先级递减)**:
  1. 首版、末版必留
  2. 命名含"修正版/重构/分支"必留
  3. 相邻字节跳变 ≥30% 时,跳变后那版必留
  4. B 类时间快照(由 J 判定单独认定)必留
  5. 命名层独立信号(如独立功能模块标记)由 J 判定个案保留
- **归档处理**:其余版本归 `corpus/.archive/<项目>/<原文件名>`,**search.py 不递归 .archive**(检索仅命中 corpus 主体,归档区不产生 noise)
- **修订关系**:**覆盖** CLAUDE.md 第 6 节"密集 vN 方向迭代族默认 B 类全留"的默认值;CLAUDE.md 那条仍适用于"未触发 G9 的版本族"(版本数 <5 或 mtime 不集中)

#### G10 中间版拷贝的"唯一物证"例外

- **判定**:跨项目目录里发现的"中间版拷贝"(不带版本号但内容相似于某已知族某中间版)默认按 A 类同族中间版处理**跳过**;**例外**——若该中间版在原族目录里没有对应快照保留(即该 mtime 时点的唯一物证),归原族保留,标"族 X 中间版填补"
- **触发条件**(四条同时满足才走例外):
  1. 文件内容明显属于某已知族(TITLE / 主导航 / 顶级章节高度同源)
  2. mtime 落在原族两份相邻快照之间
  3. 与两端最近邻快照都有可识别差异(不是任一端的精确副本)
  4. 原族在该 mtime 时段没有保留任何中间版(空白期)
- **理由**:即使是"拷贝"性质,作为某时点的唯一物证,对场景 4(找演化痕迹)和场景 1(查阅时点版本)都有独立价值

#### G11 stub 文件强制格式

- **判定**:G2 超大文件、G15 扫描类文件、G18 结构性稀薄文件,以及 G16 三件共存中的配套元数据文件,stub 内容按下列**强制格式**提升 ripgrep 命中维度
- **stub 文件名**:同位置同名 + `.stub.md` 后缀
- **关键词提炼原则**:**只从文件名拆词**,**不许打开原文读内容**(CLAUDE.md "不预处理"红线)

**stub 强制格式**:

```markdown
# <文件名(去后缀)>

- 类型: <docx/xlsx/pptx/pdf 等>
- 大小: <X KB/MB>
- mtime: <YYYY-MM-DD HH:MM>
- 源路径: <绝对路径>
- 场景: <01/02/03/04>
- 状态: <未入库正文(原因) | 已转 markdown 正文,正文在同目录 .md>
- 日期: <从文件名/mtime 提炼的关键日期>
- 与会人/对方/客户: <从文件名提炼,纪要类适用>
- 关键词: <从文件名提炼 3-5 个核心词,提升 ripgrep 命中维度>
- **LLM 处理规则**: <禁令版(stub-only):严禁推断正文内容,只能指向源文件 | 共存版(G16):本 stub 仅作元数据索引,正文在同目录 .md,不触发 stub 禁令>
```

- **源路径字段必填**:ingest.py 自动写入 ingest 时的绝对源路径
- **G16 三件共存形态(源 binary + stub + .md)**:stub 的"状态"字段需明示"已转 markdown 正文,正文在同目录 .md",**不再写"未入库正文"**(否则与同目录已落地的 .md 正文语义冲突,误导 LLM 触发 stub 禁令)
- **G15 / G18 stub 文案**:它们的正文确实未入库 .md,继续走原"未入库正文" + stub 禁令文案

#### G12 文件名编码错乱修复豁免

- **判定**:文件名是 GBK 字节被 UTF-8 错读的乱码,cp 时**修复为正确字符**写入目标
- **理由**:这是技术性瑕疵,不属于"不重命名"原则的语义干预范围
- **追溯要求**:在该文件对应的 stub 备注 / 或 cp 日志中**保留原乱码字节路径**,以备后续追溯
- **边界**:如无法确定原中文含义(乱码无法逆推),则保留原乱码不修复,且在备注里明确标注"乱码无法解码"

#### G13 模板素材三层分类

- **判定**:`03-技术决策/` 下分三层,**前缀显式区分**:
  1. **真实 ADR**(无前缀):真实项目的决策记录
  2. **示例 ADR**(`示例-` 前缀):模板里的演示性决策
  3. **工具骨架**(`工具-` 前缀):模板的元说明/工具说明,不是决策本身
- **项目前缀叠加**:若来源是某特定模板项目,加项目前缀,避免与未来其他来源的 ADR 冲突

#### G14 corpus 二级分类与文件命名规范

- **二级目录命名**:
  - 一级保持 4 个场景目录(中文,`01-历史方案` 等),不变
  - 二级 = **项目名,纯中文,与一级风格一致**
  - 未来扩展:新项目素材入库时,在对应一级目录下创建项目子目录;若项目跨场景出现,各场景目录下都开同名子目录
- **文件名前缀(替代旧的项目前缀,因目录已表达项目)**:

| 前缀 | 用途 | 适用扩展名 |
|---|---|---|
| `方案-` | 方案文档(正文 + .stub.md) | .pdf / .docx.stub.md / .pptx.stub.md / .xlsx.stub.md / .doc.stub.md / .txt / .md |
| `原型-` | 原型/工具的可交互页面;**以及主线原型的跨项目分支版/中间版** | .html(限定) |
| `章节-` | 投标技术章节 | 02 场景下所有 |
| `招标-` | 招标方/采购方下发的文件 | 询比文件 / 招标书 / 需求书 / 评分细则 |
| `决策-` | 真实 ADR | .md |
| `示例-` | 示例 ADR | .md |
| `工具-` | 工具骨架 | .md |
| `纪要-` | 会议纪要 stub | .docx.stub.md |
| `调研-` | 调研记录 / 产出 | .txt / .json / .md |
| `参考-` | 跨项目参考素材(被另一项目借鉴) | 任意 |

- **`招标-` 前缀**:主用于 02 场景,但其他场景也可能出现(例:01 场景下若客户给的需求书要单独留底)。在 prefix_rules 中,`招标-` 顺序应排在 `章节-` 之前,因为"询比"等关键词需优先于"技术方案"等命中
- **`参考-` vs `原型-` 区分**:跨项目出现的素材中——
  - **内容属另一项目、被本项目借鉴** → 用 `参考-`
  - **内容就是某项目主线的中间版/分支版,只是物理位置异常** → 用主线对应类型前缀(如 `原型-`)
  - **判断依据**:**内容归属决定前缀,不是物理位置**
- **跨项目素材的 `.references.md` 标记**:
  - 内容上属于 X 项目、物理来源是 Y 项目目录的文件 → 归 `corpus/<场景>/X项目/`
  - 在 Y 项目目录下放 `.references.md` 标记"曾用过 corpus/<场景>/X项目/<前缀>-XXX.html"
  - `.references.md` 不是 stub,只是追溯标记,不参与 ripgrep 检索
- **search.py 适配**:
  - SCENE_MAP 不变(场景代号 → 中文一级目录)
  - ripgrep 默认递归扫描,自动覆盖二级目录
  - 跳过文件:`.references.md`

#### G15 扫描类 PDF 处置

- **触发**:markitdown 转换后 .md **0 字节或 0 字符**(pdfminer 文本层为空)
- **处置**:**永久 stub 化**,源 PDF 保留 corpus 同目录;**不引入 OCR 工具**
- **依据**:轻量 skill 尺度 + 极少触发 + stub 文件名关键词已能承担指向性命中
- **解锁条件**:OCR 基建独立立项

#### G16 文本主导文档处置

- **触发**:markitdown 转换后 .md 非空 **且** 字符数 / 源字节 **≥ 5%**
- **处置**:**.md 直接入库正文,不做后处理 / 清洗**(NaN 噪声、layout 切碎段落、粗体替代 # 标题等问题对 ripgrep 字面匹配无影响,LLM 拿到带行号片段能正常理解)
- **适用范围**:docx / xlsx / pptx / PDF 文本类(跨格式统一规则)
- **5% 阈值依据**:高密度类(docx ~74% / xlsx ~112% / PDF 文本可选 ~18%)与低密度类(图形为主 ~2% / 扫描件 0%)之间存在天然空隙,5% 能干净分开两类
- **共存形态(若源是 binary)**:对 docx / xlsx / pptx / PDF 这类二进制源,**源 + .stub.md + .md 三件同目录共存**——源是 binary 不可 ripgrep / stub 是文件存在性标记 / .md 是检索正文

#### G17 保留(不立)

NaN 噪声不影响 ripgrep 字面匹配,LLM 整合答案时主动忽略即可。G17 编号保留以备未来如确需再启用。

#### G18 结构性稀薄文档处置

- **触发(双条件 AND)**:markitdown 转换后 .md **字符密度 < 5%** **且** **字符总数 < 2000**
  - 任一条件不成立 → 走 G16(包括衰减性稀薄:密度低但字符数足,内容上仍可入库检索;典型例:带覆层的 PDF)
- **处置**:**永久 stub 化**,**不入库 .md**(即使有非空 .md 输出);若源已在 corpus,维持 stub;若源不在 corpus,不动
- **依据**:形状 / 连线 / 位置等图形元素载体的信息无法 ripgrep 命中;LLM 拿到孤立标签集合无法重建关系语义;轻量 skill 尺度无替代(多模态图形理解需 vision LLM 基建)
- **与 G15 关系**:并列各管一段——G15 处置"扁平失败"(0 字节,源是图像扫描件),G18 处置"结构性稀薄"(密度 < 5% 且字符数 < 2000,源是图形为主文档);两者共同点是"轻量方案的轻量手段触不到核心信息"
- **解锁条件**:多模态 LLM 图形理解基建
