# 场景 3:技术决策溯源

> 当用户跨项目问"我们到底用了什么"、"为什么选 X"、"那个项目 Y 怎么实现的"——精确定位决策记录及其上下文。

---

## 素材形态

`corpus/03-技术决策/` 下主要是:

- ADR(Architecture Decision Record)
- 技术选型记录、调研对比表
- 方案中的"关键技术决策"章节抽出
- 项目踩坑记录、技术风险清单

**注意**:ADR 通常很短(每份几百字),信息密度高,命中后基本就能直接答。

---

## 检索词层级偏好(agent loop 起点粒度)

本场景目标是"精确定位决策点 + 决策原因",**首选字段词/技术名(细粒度,高精度优先)**:

- 第 1 轮检索词以具体技术名 / 产品名 / 决策点字段为起点(如"Kingbase"、"信创替代"、"PostGIS 兼容")
- 命中过多极少出现(ADR 文件本身少且短);若命中过多,沿"技术名 → 技术名+项目限定词"方向收窄
- 命中 0 时,沿"技术名 → 上位概念(数据库选型/中间件选型)"方向扩展;扩展不可跳得太远,防止跨决策类别命中

---

## 检索关注点

用户来这个场景是**找精确答案**,不是找参考。所以:

1. **决策点本身**:用了什么、选了什么、做了什么
2. **决策原因**:为什么这么决定(对比了哪些选项、关键判断依据)
3. **风险/坑**:决策落地后遇到的问题(这是最高价值信息)
4. **决策时间和项目**:同一类决策可能多个项目都有,且结论可能不同(比如 A 项目用 PostGIS,B 项目用 KingbaseGIS)

---

## 输出格式

```
【决策结论】
A 项目(2024 年某省规自厅项目)使用 Kingbase V8R6 + KingbaseGIS 作为信创替代数据库。

【原因】
- 客户明确要求信创适配,排除 PostgreSQL
- 对比了达梦、人大金仓、Kingbase,选 Kingbase 因为...(具体)
[corpus/03-技术决策/A项目-数据库选型.md:15-22]

【已知坑 / 风险】
- KingbaseGIS 部分空间函数语法和 PostGIS 不兼容,迁移时改了 N 处
- 性能在 XX 场景下比 PostGIS 慢约 30%
[corpus/03-技术决策/A项目-数据库选型.md:35-44]

【相关决策】(如果跨项目结论不一致)
- B 项目(2023)同类需求选了达梦 → [引用]
- 差异原因:客户偏好不同
```

---

## 特殊注意

- 决策点和原因要分开列,原因部分必须带引用
- 如果只找到决策点没找到原因,**明确说明"未找到决策原因记录"**,不要编造
- 跨项目同类决策结论冲突时,**全部列出**,让用户自己判断哪个适用当前项目
- 风险/坑部分如果有,一定要展开——这是 ADR 类素材最稀缺也最值钱的部分

---

## L3 stub 兜底关注字段

L1/L2 均无命中、降级到 L3 stub 元数据扫描时,本场景重点关注 stub 文件的下列字段:

- `关键词`(从文件名拆出的技术名 / 决策名,如"数据库选型"、"中间件适配")
- `源路径`(原决策文件位置,决策原因不在 stub 中,**必须打开原文件**)

answer 中如基于 L3 stub,必须明示"原文件未入库正文,**仅 stub 关键词指向决策点存在,决策原因/对比/风险均无法从 stub 推断**,建议打开原文件"。**本场景的 stub 兜底告知力度要强于其他场景**——技术决策溯源的核心信息(为什么、踩了什么坑)是绝不允许编造或推测的。
